## v1 Requirements — Final Status

### Architecture

- [x] **ARCH-01**: Maintainer can enforce explicit dependency direction between `Agent`, `Application`, `DomainService`, `Infrastructure`, and `Web` layers.
  - **Outcome:** ✅ Validated — ArchUnitNET guardrails in Phase 1. Executable rules covering Quartz job reach-through, application-to-web/scheduler dependencies, and domain/host leakage.
- [x] **ARCH-02**: Maintainer can keep `Web` and `Console` hosts thin so startup code no longer owns business orchestration decisions.
  - **Outcome:** ✅ Validated — Phase 2 Plan 03. Thin-host delegation assertions prove Console and Quartz jobs delegate to application services.
- [x] **ARCH-03**: Maintainer can compose core modules through module-level service registration entry points instead of broad direct wiring in host `Program` files.
  - **Outcome:** ✅ Validated — Phase 1 Plan 02. Host-local grouping seams (`AddBiliConsoleModules`, `AddBiliWebModules`) over existing `Add*` seams.
- [x] **ARCH-04**: Maintainer can evolve EF, HTTP Agent, and notification integrations behind clearer adapter or port boundaries.
  - **Outcome:** ⚠ Partially validated — Phase 6. EF: IExecutionLogRepository + IUserRepository established. HTTP Agent: BiliResiliencePolicies with split policies. Notification: deferred — still direct Serilog sink dependency.

### Testing

- [x] **TEST-01**: Maintainer can freeze the current observable behavior of critical `Login` and `DailyTask` flows with characterization tests before refactoring them.
  - **Outcome:** ✅ Validated — Phase 2 Plan 02. LoginTask and DailyTask characterization tests with controlled doubles and diagnostic assertions.
- [x] **TEST-02**: Maintainer can validate startup, configuration binding, EF, HTTP integration, and scheduling through host-level integration tests.
  - **Outcome:** ✅ Validated — Phase 2 Plan 03. Web and Console startup integration tests + thin-host delegation safety assertions.
- [x] **TEST-03**: Maintainer can detect new cross-layer dependency violations through automated architecture tests.
  - **Outcome:** ✅ Validated — Phase 1 Plan 01. DependencyGuardrailTests with ArchUnitNET; 4/4 passing throughout milestone.

### Refactor Flows

- [x] **FLOW-01**: Maintainer can refactor the `Login` flow behind a clearer application boundary without changing observable behavior.
  - **Outcome:** ✅ Validated — Phase 3 Plan 01. LoginTaskAppService clarified with XML docs; all characterization tests pass.
- [x] **FLOW-02**: Maintainer can refactor the `DailyTask` flow behind a clearer and testable application flow without changing observable behavior.
  - **Outcome:** ✅ Validated — Phase 4 Plan 01. DailyTaskAppService clarified with XML docs; characterization tests pass.
- [x] **FLOW-03**: Maintainer can reduce Quartz job classes to thin scheduling shells that delegate to application use cases.
  - **Outcome:** ✅ Validated — Phase 5 Plans 01-02. All 12 Quartz job classes: primary constructor + static JobKey + single-line expression-body DoExecuteAsync.
- [x] **FLOW-04**: Maintainer can access Bilibili HTTP integrations through a more consistent Agent boundary with explicit policies and handlers.
  - **Outcome:** ✅ Validated — Phase 6 Plan 01. BiliResiliencePolicies with ReadOnlyPolicy/MutatingPolicy split, 30s explicit timeout, 4 side-effecting clients switched to MutatingPolicy.

### Quality

- [x] **QUAL-01**: Maintainer can distinguish expected failures, integration failures, and unexpected crashes through a clearer exception model.
  - **Outcome:** ✅ Validated — Phase 6 Plans 01, 03, 04. BiliException hierarchy; 14 DomainService throws converted; BiliCookie/CookieInfo sweep complete; 8 unit tests.
- [x] **QUAL-02**: Maintainer can compare and diagnose old versus refactored critical paths using added logs and diagnostic signals.
  - **Outcome:** ✅ Validated — Phase 2 Plan 02. TaskFlowDiagnosticScope with FlowStart/FlowCompleted/FlowFailed markers in LoginTaskAppService and DailyTaskAppService.
