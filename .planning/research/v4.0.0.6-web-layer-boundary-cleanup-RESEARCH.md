# Research: v4.0.0.6 Web Layer Boundary Cleanup

**Date:** 2026-05-05
**Milestone:** v4.0.0.6 Web Layer Boundary Cleanup
**Focus:** Separate Web UI concerns from business orchestration without changing observable Web behavior.

## Research Question

How should the current Blazor and ASP.NET Core Web layer be refactored so Razor pages and dialogs stop owning workflow orchestration, direct repository access, and long-running UI coordination, while still preserving the current host behavior and enabling targeted Web tests?

## Current Codebase Findings

### 1. The Web composition root is still broad and mixes many startup concerns

Observed in `src/Ray.BiliBiliTool.Web/Program.cs`:

- configuration overlay
- EF registration
- Serilog setup
- Quartz setup
- Web service registration
- Blazor and controller registration
- startup initialization
- Swagger wiring

This is acceptable as a composition root, but it is still the broadest host entry point in the repository and remains a likely dumping ground if milestone work moves business coordination into startup wiring instead of explicit Web-facing services.

### 2. Several Razor component code-behind files own orchestration instead of only UI state

Observed examples:

- `Components/Pages/Login.razor.cs` parses query-string error state and owns password-visibility state.
- `Components/Pages/Admin.razor.cs` performs validation, invokes `IAuthService`, handles success and error messages, waits two seconds, then performs logout navigation.
- `Components/Pages/Schedules/Schedules.razor.cs` registers scheduler event listeners, maintains a mutable grid-backed collection, coordinates refresh flows, and translates scheduler state into UI actions.
- `Components/Pages/Schedules/LogsDialog.razor.cs` directly reads `IExecutionLogRepository`, owns timer-based polling, cancellation lifetime, and log refresh error handling.
- `Components/Pages/Schedules/HistoryDialog.razor.cs` owns paging state, data loading, and execution-log presentation helpers.

The pattern is not just "code-behind exists". The issue is that components directly coordinate domain or infrastructure-facing behavior instead of delegating through a thinner Web-layer seam.

### 3. The repository already has a small Web-specific service seam, but it is too narrow

Observed in `src/Ray.BiliBiliTool.Web/Services/AuthService.cs` and `Extensions/ServiceCollectionExtension.cs`:

- `IAuthService` is a useful Web-layer abstraction.
- It already shields the page from direct repository access for auth concerns.
- However, page-level validation, navigation, success timing, and display-state orchestration still live in `Admin.razor.cs`.

Implication: the milestone should expand this pattern instead of inventing a new architecture style.

### 4. Scheduler pages and dialogs are the clearest Web-boundary hotspot

The schedule screens combine UI rendering, event subscription, polling, dialog control, and direct reads from execution-log services or repositories. This makes them hard to test and easy to regress.

This slice is a better target than a broad repo-wide "clean up Web" effort because:

- it is operationally important
- it is highly interactive
- it shows clear UI/business coordination mixing
- it can be validated with focused tests and existing host integration coverage

### 5. There is no existing component-test stack in source-controlled test projects

Repository search did not find `bUnit` package references in `*.csproj` files.

Implication: if this milestone expects targeted Web or Blazor testing, it must add the minimal test harness explicitly instead of assuming it already exists.

## External Guidance

### Microsoft Blazor guidance

Microsoft's Blazor guidance centers the framework on components that define rendering logic and handle user events. That supports component-oriented UI composition, but it does not require business or repository orchestration to live in the component itself. For this repo, the important implication is that UI event handling should remain in the component, while longer-running workflow coordination and infrastructure-facing logic should move behind dedicated services or presenters owned by the Web layer.

### bUnit guidance

bUnit is the standard approach for Blazor component testing with xUnit. It renders components under test, injects services, passes parameters, and verifies semantic markup or interaction behavior. That makes it a good fit for this milestone if the repo adds targeted tests for:

- login or admin form validation and state transitions
- scheduler dialog rendering and user-triggered actions
- component output that depends on injected Web-facing services

bUnit does not replace host integration tests. It complements them by covering page or dialog behavior without booting the entire app.

## Recommended Direction

### In scope for v4.0.0.6

1. Introduce explicit Web-facing coordination seams for the targeted pages and dialogs.
2. Keep Razor components responsible for rendering, event binding, and display state only.
3. Move scheduler log/history loading and refresh coordination out of dialog components.
4. Move auth/admin validation and success-flow orchestration out of component code-behind where practical.
5. Add a focused component-test harness for the refactored Web slices.
6. Keep the Web host composition root wiring-focused and avoid moving feature logic into registration code.

### Out of scope for v4.0.0.6

- full Web UI redesign
- microservice or host split
- replacing MudBlazor
- repo-wide test-framework churn
- general cleanup unrelated to Web UI/business separation
- deferred notification-boundary work unless it becomes a direct blocker for the selected Web slices

## Proposed Milestone Shape

### Phase candidate 1: Web boundary foundation

- define the Web-layer seam pattern for targeted components
- add the first dedicated Web component-test harness
- codify where direct repository or orchestration logic is no longer allowed in the selected slices

### Phase candidate 2: Auth and admin slice cleanup

- isolate login/admin form workflow logic
- keep navigation and validation behavior intact
- make the slice testable without full-host bootstrapping for every behavior check

### Phase candidate 3: Scheduler slice cleanup

- move event subscription, log polling, and execution-history loading behind explicit Web-facing services or coordinators
- keep MudBlazor dialog behavior and scheduler UI output stable

### Phase candidate 4: Composition and regression cleanup

- finish any required Web host wiring cleanup
- confirm the refactored slices still pass build, architecture, host integration, and new Web tests

## Risks To Control

- Moving logic from components into startup or DI lambdas instead of real Web-facing services.
- Introducing hollow interfaces that only rename existing code paths without reducing direct component dependencies.
- Adding component tests that lock down incidental markup details instead of meaningful behavior.
- Expanding scope into general Web modernization instead of keeping the milestone centered on UI and business separation.

## Requirement Implications

The milestone requirements should explicitly cover:

- Web-layer orchestration seams
- scheduler dialog and page coordination cleanup
- auth and admin page workflow cleanup
- focused Web component or slice tests
- final regression safety checks

The milestone should not claim success based only on file moves or namespace cleanup. It should require observable reduction of component-owned orchestration in the targeted slices.
